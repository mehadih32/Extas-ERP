## K2 · EXTAS ERP-এর মানচিত্র (Mehedi 2.0-এর জন্য)

EXTAS ERP হলো EXTAS বায়িং হাউসের নিজের সফটওয়্যার। বিক্রি, উৎপাদন (CM), কাঁচামাল, স্টক, হিসাব, HR আর কাগজপত্র এক জায়গায় চলে। একাধিক কোম্পানি থাকলে প্রতিটির ডেটা আলাদা থাকে। স্ট্যাক: Next.js (App Router, TypeScript), Prisma, PostgreSQL 16, Tailwind ও shadcn/ui। কোডে আছে 135টি Prisma model, 101টি enum, 49টি permission key, আর 406টি route ফাইলে 539টি API handler। ডিপ্লয়: একটি Azure Ubuntu 24.04 সার্ভার। Docker-এ চলে db (PostgreSQL), migrate, app আর caddy (HTTPS)। GitHub-এ main branch-এ merge হলেই "Deploy" workflow নিজে থেকে `deploy/auto-deploy.sh` চালিয়ে নতুন কোড বসায়। ডেটা থাকে `/srv/extras-erp`-এ, রোজ 02:00-এ (বাংলাদেশ সময়) ব্যাকআপ হয়।

**Mehedi 2.0 কীভাবে ব্যবহার করবে**

- এটি "কোথায় কী আছে" তার মানচিত্র। কোনো কাজের আগে এখানে route, method আর permission key দেখে নাও।
- সত্যের উৎস কোড (শেষ commit `0b0f691`, তারিখ 2026-10-14)। README বা Help Center-এর সাথে না মিললে কোড মানো।
- ERP-তে ঢোকো নিজের আলাদা user দিয়ে, মালিকের user দিয়ে নয়। তাহলে AuditLog-এ বোঝা যাবে কোন কাজ AI করেছে।
- লগইন: `POST /api/auth/login` { email, password }। উত্তরে cookie `extras_session` আসে। এটি 30 দিন চলে, ব্যবহার করলে মেয়াদ বাড়ে। ERP-তে কোনো API key বা token নেই।
- সাবধান: 5 বার ভুল পাসওয়ার্ড দিলে 15 মিনিট লক। এক IP থেকে মিনিটে 10 বারের বেশি লগইন চেষ্টা করা যায় না।
- নতুন user হলে আগে পাসওয়ার্ড বদলাতে হয় (`POST /api/auth/change-password`), নইলে সব route `PASSWORD_CHANGE_REQUIRED` দেয়।
- AI-এর user-কে কোনো Employee রেকর্ডের সাথে জুড়ো না। জুড়লে কোম্পানির চাকরির শর্তাবলি (terms) মানতে হবে, না মানা পর্যন্ত সব route `TERMS_REQUIRED` দেয়।
- সব কাজ হয় active company-তে। কোম্পানি বদলাতে `POST /api/auth/switch-company` { companyId }। তোমার কী কী permission আছে দেখতে `GET /api/auth/me`।
- প্রতিটি উত্তর হয় `{ ok: true, data }` অথবা `{ ok: false, error }`। error code: `FORBIDDEN` (403), `NOT_FOUND` (404), `VALIDATION` (422), `CONFLICT` (409), `INSUFFICIENT_STOCK` (409), `RATE_LIMITED` (429), `UNAVAILABLE` (503), `UNAUTHENTICATED` (401)।
- কোন body-তে কী field লাগে, তা route ফাইলের মন্তব্যে আর module-এর `schemas.ts` (zod) ফাইলে লেখা আছে। আন্দাজে field পাঠাবে না।
- তুমি কখনো কিছু মুছবে না। section 5-এর কোনো route নিজে ডাকবে না। দরকার হলে মালিককে "মোছার অনুরোধ" পাঠাবে।
- টাকা লুকানোর নিয়ম মানো (section 3)। যে টাকা তোমার role দেখে না, তা আন্দাজ করে বলবে না।
- কিছু কাজ শুধু Server Action দিয়ে হয়, REST route নেই (section 7)। ওগুলো তুমি এখন ডাকতে পারবে না।
- কোডের মন্তব্যে "buyer" শব্দটি কখনো কেনাকাটার লোক (যার `materials.purchase` আছে) বোঝায়, গার্মেন্টসের ক্রেতা নয়। প্রসঙ্গ দেখে বুঝবে।
- নিশ্চিত না হলে লিখবে "(কোডে নিশ্চিত হইনি)"। আন্দাজে কাজ করবে না।

### 2. ব্যবসার মূল প্রবাহ

**(a) ক্রেতার অর্ডার থেকে উৎপাদন শুরু**

1. ক্রেতা খোঁজো: `GET /api/parties?kind=BUYER&search=`। না থাকলে নতুন: `POST /api/parties` (`parties.manage`)।
2. স্টাইল ও SKU ঠিক আছে কি না দেখো: `GET /api/inventory/styles?search=`। নতুন স্টাইল: `POST /api/inventory/styles`, তারপর রং-সাইজ: `POST /api/inventory/styles/:styleId/matrix` { colorIds, sizeIds } (`inventory.manage`)। target grid-এর জন্য SKU লাগে।
3. Quotation: `POST /api/sales/quotations` (`sales.quotation.manage`)। প্রতিটি item-এ description, fabric, gsm, colorNote, sizeRatio, accessories, imageId, sizeBreakdown, quantity, unitPrice থাকতে পারে। styling rule (যেমন "Placket should not have a black border") যায় stylingRules-এ। রেফারেন্স ছবি আগে তোলো `POST /api/sales/reference-images` দিয়ে (JPG বা PNG, 512 KB আর 2400 pixel পর্যন্ত)।
4. Quotation-এর অবস্থা: `PUT /api/sales/quotations/:quotationId/status` { SENT | ACCEPTED | REJECTED }।
5. Proforma: `POST /api/sales/quotations/:quotationId/convert` { advancePercent? }। অগ্রিম ডিফল্টে 30% (Company.defaultAdvancePercent)। ক্রেতার PO নম্বর, মেয়াদ, ব্যাংক: `PATCH /api/sales/proformas/:proformaId`।
6. অগ্রিম টাকা: `POST /api/sales/payments` { proformaId, amount, method } (`accounts.receipts.record`)। পুরো অগ্রিম এলে ERP নিজেই একটি ProductionProject খোলে, proforma হয় `IN_PRODUCTION`, লক্ষ্য দিন ধরে 45 দিন পরে। আগে হাতে project খোলা থাকলে নতুন খোলে না।
7. Order: proforma থেকে `POST /api/sales/proformas/:proformaId/convert` { lines বা matrix } (`sales.order.create`), অথবা সরাসরি `POST /api/sales/orders` { channel (যেমন `B2B_PREORDER`, `WHOLESALE`), partyId, lines বা matrix }।
8. "Start production": order বা proforma-র পাতার বোতাম `/production/projects/new?order=<id>` (বা `?proforma=<id>`) খোলে। সংরক্ষণ করলে ডাকে `POST /api/production/projects` { name, styleId, factoryId, buyerId, targetDate, targets: [{ variantId, quantity }], salesOrderId অথবা proformaId, batchId?, status: PLANNED | ACTIVE } (`production.manage`)।
9. "Start production"-এর নিয়ম: order-এ নাম থাকা ক্রেতা লাগে (walk-in নয়), আর order-এর অবস্থা `DRAFT`, `CONFIRMED` বা `PROCESSING` হতে হবে। proforma `CANCELLED` বা `CONVERTED` হলে চলে না। grid-এ বসে যা বানানো বাকি: order-এর পিস, বাদ যা ডেলিভারি হয়েছে আর অন্য project যা বানাচ্ছে।
10. Master batch: `POST /api/production/batches` { name, kind: CM | READYMADE | DROPSHIP, factoryId, targetDate, rejectTolerancePercent (ডিফল্ট 2) }। কোড হয় `MB-2026-00001` ধরনের।
11. batch-এ style যোগ: প্রতিটি style একটি ProductionProject, তার batchId থাকে। স্ক্রিনে `/production/projects/new?batch=<id>`; API-তে project তৈরির সময় batchId দাও, বা পরে `PATCH /api/production/projects/:projectId` { batchId }।
12. target lines: ProductionTargetLine (variantId, quantity)। বদলাতে `PATCH /api/production/projects/:projectId` { targets } (পুরো grid বদলে যায়)। এক পিসের লক্ষ্য দাম targetUnitCost। cost guard 85%-এ হলুদ, 100% পেরোলে লাল আর ইনবক্সে বার্তা।
13. ধাপ এগোনো: `POST /api/production/projects/:projectId/stage` { stage } (FABRIC_SOURCING → CUTTING → SEWING → WASH_QC → FINISHING)। পেছনে গেলে note লাগে। হোল্ড/চালু: `POST .../status` { ACTIVE | ON_HOLD }। cutting ও sewing-এর শেষ দিন: `PATCH .../milestones` { cutBy, sewBy }।
14. প্রতি পিসের কাঁচামাল ও টেক প্যাক: `PUT /api/production/projects/:projectId/material-needs`, তারপর PDF `GET /api/production/projects/:projectId/tech-pack`।

**(b) কাঁচামালের হিসাব থেকে বুকিং, মাল গ্রহণ, বিল, পরিশোধ**

1. প্রতি পিসে কী লাগে: `PUT /api/production/projects/:projectId/material-needs` { needs: [{ materialId, perPiece, wastagePercent, split: TOTAL | COLOUR | COLOUR_SIZE, placement, imageId, notes }] }। এটি আগের সব লাইন বদলে দেয়।
2. পুরো batch-এ কী লাগবে আর কী অর্ডারে আছে: `GET /api/production/batches/:batchId/materials`।
3. কাপড় (আর কলার-কাফ) বুকিং: `POST /api/production/bookings` { source: SUPPLIER_PO | MARKET_PURCHASE, category: KNITWEAR | WOVEN | OUTERWEAR | SWEATER | OTHER, supplierId, batchId?, lines (specs: GSM, DIA, composition, yarn count...), collar ছক, terms, termsLanguage: EN | BN }। permission: `production.bookings.supplier` (মিল বা ট্রিমস হাউস) বা `production.bookings.market` (বাজার থেকে কেনা)।
4. একটি বুকিং মানে একটি PurchaseOrder আর একটি Booking। কলার-কাফের ছক থাকে BookingCollarSize (সাইজ গ্রুপ, যেমন S-M: 42 x 9 cm), BookingCollarColour (পোশাকের রং, কলারের রং, tipping) আর BookingCollarQuantity (পিস ও সেট) টেবিলে। collarExtraPercent দিয়ে বাড়তি সেট হিসাব হয়।
5. বুকিং PDF (স্পাইরাল বাঁধাইয়ের মতো): `GET /api/production/bookings/:bookingId/pdf`। দাম দেখার অনুমতি না থাকলে দাম ছাড়া ছাপে।
6. batch-এ বুকিং যোগ: `POST /api/production/bookings/:bookingId/attach` { batchId } (`production.bookings.attach`)। লাইনগুলো style ধরে ভাগ হয় (PurchaseOrderLineShare)।
7. batch-এর ট্রিমস ও এক্সেসরিজ: `POST /api/production/batches/:batchId/orders` (`materials.purchase`), প্রতি সরবরাহকারীর জন্য একটি PO। একক PO: `POST /api/materials/purchase-orders`।
8. বুকিং বদল: মাল আসার আগে `PATCH /api/production/bookings/:bookingId` (পুরো বুকিং বদলায়)। মাল আসার পরে শুধু কাগজ: `PATCH /api/production/bookings/:bookingId/paperwork`।
9. মাল গ্রহণ (batch-এর জন্য এক জায়গায়): `GET` তারপর `POST /api/production/batches/:batchId/receive` { orderId, lines: [{ lineId, challanQuantity, quantity, unitPrice? }] } (`materials.purchase`)। এতে Due বিল (SupplierBill) হয়, মাল স্টোরে ঢোকে। ছাড়ের বেশি কম এলে সরবরাহকারীর Fault log-এ `SHORT_RECEIVE` ওঠে।
10. batch-এর বাইরে মাল গ্রহণ: `POST /api/materials/purchases` (বিলসহ, `materials.purchase` অথবা নগদে কিনলে `accounts.payments.record`)।
11. স্টোর থেকে style-এ ইস্যু: `POST /api/production/batches/:batchId/issue` (`materials.manage`), অথবা একটি project-এ `POST /api/materials/issues`। বেঁচে যাওয়া মাল ফেরত: `POST /api/materials/issues/returns`।
12. অন্য বিল (CM, ধোয়া, পরিবহন...): `POST /api/production/bills` { supplierId, paymentType: DUE | CASH_BANK, allocations: [{ projectId, expenseHeadId, amount }] }। এক বিল কয়েকটি project-এ ভাগ করা যায়। ডিফল্ট খাত: Fabric, Trims & Accessories, Cutting, Sewing (CM), Wash, Print & Embroidery, Finishing & Packing, Production Transport, Sampling, FOB Goods, QC & Inspection, Other Production Cost।
13. টাকা দেওয়া (সব `accounts.payments.record`): কাঁচামালের বিলে `POST /api/materials/purchases/:billId/payments`, উৎপাদনের বিলে `POST /api/production/bills/:billId/payments`, সরবরাহকারীর হিসাবে `POST /api/accounts/supplier-payments` (পুরোনো বিল আগে শোধ হয়, বাড়তি টাকা অগ্রিম থাকে)।
14. খারাপ মাল ফেরত: `POST /api/materials/supplier-returns` { billId, reason, lines } (ডেবিট নোট)।
15. বুকিং বন্ধ বা বাতিল (`production.bookings.close`) আর PO বন্ধ বা বাতিল (`materials.purchase`): এগুলো section 5-এর কাজ, মালিককে অনুরোধ।

**(c) ফ্যাক্টরির চুক্তি, CM, cutting, finishing, embroidery, ফল্ট, settlement**

1. চুক্তির তালিকা ও বাকি খসড়া: `GET /api/production/batches/:batchId/contracts`। নতুন খসড়া: `POST` একই route-এ { kind: FABRIC | ACCESSORIES | FACTORY_CM, partyId }। নম্বর হয় `AGR-2026-00001` ধরনের। AI চালু থাকলে ধারাগুলো AI সহজ ইংরেজিতে লেখে।
2. চুক্তি বদল ও CM রেট: `PATCH /api/production/contracts/:contractId` { clauses, signedOn?, cmRates: [{ projectId, cmRate }] }। CM থাকে ProductionProject.cmRate-এ। PDF: `GET /api/production/contracts/:contractId/pdf`।
3. ফ্যাক্টরিকে অগ্রিম CM: `POST /api/production/batches/:batchId/payments` (`accounts.payments.record`)।
4. ফ্যাক্টরিতে কী পাঠানো হলো (চালান): `POST /api/production/projects/:projectId/challans` { items: [{ description, quantity, unit }] }। নম্বর `MC-`। এতে স্টক বা টাকা নড়ে না।
5. Cutting report: `POST /api/production/projects/:projectId/cutting` { cutOn, lines: [{ colorName, sizeName, quantity }], fabricUsed, photoId? }। সাথে সাথে কাপড়, কলার-কাফ আর এক্সেসরিজের সাথে মিলিয়ে কম পড়লে সতর্কবার্তা দেয়।
6. cutting sheet-এর ছবি AI দিয়ে পড়া: আগে ছবি তোলো `POST /api/production/files` (JPG, PNG, WebP বা PDF, 10 MB), তারপর `POST /api/production/projects/:projectId/cutting/read` { photoId }। কিছু সংরক্ষণ হয় না, মিলিয়ে তারপর report সেভ করতে হয়।
7. Embroidery বা print-এ পাঠানো: `POST /api/production/projects/:projectId/embroidery` { kind: EMBROIDERY | PRINT, partyId, lines }। ফেরত: `POST /api/production/embroidery/:jobId/receive` { lines: [{ received, spoiled }] }। নষ্ট পিস আবার কাটা: `POST /api/production/embroidery/:jobId/replace` { lines, logFault? }। EMBROIDERY_PRINT ধরনের সরবরাহকারীর নষ্ট করা পিসের দাম তার Supplier Due থেকে কাটে।
8. কাপড়ের ত্রুটি: `POST /api/production/projects/:projectId/fabric-faults` (Fabric Fault Note)। হাতে ফল্ট: `POST /api/production/faults`। কাটা বা ছাড়: `PATCH /api/production/faults/:faultId` { status: DEDUCTED | WAIVED | OPEN }।
9. Finishing গণনা: `POST /api/production/projects/:projectId/finishing` { lines: [{ colorName, sizeName, a, b, c, reject }] }। মেরামত থেকে ফেরত: `POST .../finishing/mending`।
10. পুরো packing list গ্রহণ: `POST /api/production/projects/:projectId/finishing/packing-list` { missing?, warehouseId?, closeStyle? } (`production.stock_intake`)। শুধু A ও B পিস বিক্রির স্টকে যায় (StockIntake আর StockLot হয়)। হারানো পিস ফ্যাক্টরির ফল্ট (`MISSING_PIECES`) হয়। এক পিসের শেষ খরচ = মোট খরচ ÷ (A + B)।
11. অন্য পথ (ডেলিভারি খসড়া): `POST /api/production/intakes` (খসড়া), দরকারে `PATCH`, তারপর `POST /api/production/intakes/:intakeId/confirm`।
12. batch-এর খরচ (QC, যাতায়াত): `POST /api/production/batches/:batchId/costs` { split: EQUAL | ONE }।
13. শেষ CM হিসাব: খসড়া দেখো `GET /api/production/batches/:batchId/cm-settlement`, সেভ করো `POST` একই route-এ { deductCGrade, note }। নম্বর `CMS-`। এতে কাটে: খোলা ফল্ট, ছাড়ের (ডিফল্ট 2%) বেশি reject (style-এর target price-এ), চাইলে C-grade-এর CM, আর আগে দেওয়া অগ্রিম ও পরিশোধ। সেভ করলে Dr Payable / Cr Deductions from Suppliers journal হয়। PDF: `GET /api/production/cm-settlements/:settlementId/pdf`।
14. batch-এর টাকার গল্প: `GET /api/production/batches/:batchId/summary` (আর `/pdf`)। সরবরাহকারীর 12 মাসের রিপোর্ট কার্ড: `GET /api/production/suppliers/:supplierId/report-card`।
15. style শেষ করা: `POST /api/production/projects/:projectId/complete`। বাকি খরচ write off করতে `accounts.manage` লাগে। project ধরে হিসাব হয় এমন সরবরাহকারীর (FABRIC, FOB, CM) জন্য ProjectSettlement তৈরি হয়।

11. মাল ফেরত (ইনভয়েস থেকে): `POST /api/sales/returns` { invoiceId, items: [{ orderItemId, quantity }], reason } (`accounts.receipts.record`)। ক্রেডিট নোট `CN-`, পিস যায় Damage & QC Rejects-এ।

13. Courier ও shipment: Shipment, CourierAccount model আছে, কিন্তু Pathao/Steadfast-এর কোনো কোড নেই। ফেরত পার্সেলের QC pool নেই (`sales.returns.qc` key আছে, কোথাও ব্যবহার নেই)।
14. নিষ্ক্রিয় ক্রেতা ফেরানো: `GET /api/parties/dormant`, campaign `POST /api/parties/campaigns`। ERP শুধু WhatsApp (wa.me), mailto বা sms লিংক বানায়; পাঠানো হাতে, তারপর "sent" চিহ্ন।

**(e) হিসাব (Accounts)**

1. খাতার তালিকা ও লেজার: `GET /api/accounts/chart`, `GET /api/accounts/chart/:accountId/ledger`। নতুন খাত: `POST /api/accounts/chart` (`accounts.manage`)।
2. জার্নাল: দেখা `GET /api/accounts/journal`, হাতে ভাউচার `POST /api/accounts/journal` { description, lines: [{ accountId, debit, credit }] } (`accounts.manage`)। ভুল উল্টানো (`POST .../reverse`) section 5-এর কাজ।

### 3. পারমিশন

**কীভাবে কাজ করে**

- Permission: একটি ক্ষমতা, যেমন `production.manage`। সব key আছে `src/modules/rbac/permissions.ts`-এ, seed করলে Permission টেবিলে যায়।
- Role: কোম্পানির ভেতরের ভূমিকা। 6টি built-in: Super Admin, Production Manager, Sales Executive, Warehouse Team, Employee, Accounts। নিজের মতো role-ও বানানো যায়।
- RolePermission: কোন role কোন key পায়।
- CompanyMembership: একজন user এক কোম্পানিতে একটি role-এ থাকে।
- MemberPermission: একজনের জন্য আলাদা বদল। `granted: true` মানে role-এ নেই এমন key যোগ, `false` মানে role-এর key সরানো। role বদলালে এগুলো মুছে যায়।
- হিসাব (`rbac/resolve.ts`): platform owner (User.isSuperAdmin) বা Super Admin role সব key পায়। অন্যরা পায় role-এর key, তার ওপর নিজের বদল।
- Super Admin-এর permission কমানো যায় না। একজন নিজের permission নিজে বদলাতে পারে না। শেষ Super Admin-কে সরানো যায় না। built-in role-এর নাম বদলানো বা মোছা যায় না।
- স্ক্রিনে permission দেখায় গাছের মতো: Main area > sub-area > action (`src/components/settings/roles/access-tree.ts`, ACCESS_TREE)। Mehedi 2.0-এর control tree এর ওপরেই বানানো যায়।
- route-এ যাচাই: `requirePermission(...)` (সবগুলো লাগে) বা `requireAnyPermission(...)` (যেকোনো একটি)। কিছু route শুধু লগইন চায় (`requireCompany`), কিছু শুধু platform owner (`requirePlatformSuperAdmin`)।
- সাবধান: `company.roles.manage` যার আছে, সে যেকোনো role-কে (নিজের role সহ, Super Admin ছাড়া) সব key দিতে পারে। তাই AI-এর হাতে এটি গেলে নিজের ক্ষমতা নিজে বাড়ানোর পথ খোলে।
- সাবধান: আলাদা "delete" key নেই। যেমন `production.manage` দিয়েই batch, চুক্তি, cutting report মোছা যায়। তাই "AI মুছবে না" নিয়ম RBAC দিয়ে আটকানো যায় না; AI-এর tool layer-এ আটকাতে হবে।

কিছু খুঁটিনাটি:

- AI পড়লে কিছুই নিজে স্টকে ওঠে না। মানুষ মিলিয়ে confirm করলে তবেই ওঠে। AI-এর কাঁচা উত্তর থাকে StockIntake.aiRawResult-এ, ভরসা aiConfidence-এ, method হয় `AI_OCR`। cutting-এ থাকে CuttingReport.readByAi।
- Deliveries স্ক্রিন এখন `parse: false` পাঠায়। মানে packing list AI দিয়ে পড়া API-তে আছে, স্ক্রিনে ব্যবহার হয় না। cutting sheet পড়া স্ক্রিনে আছে।

- AI-এর খরচ বা token কোথাও গোনা হয় না। module ধরে on/off নেই। সব কাজে একটিই চাবি।

### 6. Mehedi 2.0-এর টুলের তালিকা (প্রস্তাব)

চিহ্ন: R = শুধু পড়া, W = লেখা। "মালিক" কলামে: না = নিজে করতে পারে; হ্যাঁ = ডিফল্টে মালিকের অনুমতি লাগবে; অনুরোধ = নিজে কখনো ডাকবে না, মালিককে অনুরোধ পাঠাবে। হ্যাঁ লাগে: টাকা বাইরে যাওয়া, দাম বা CM বাঁধা, ক্রেতা বা সরবরাহকারীকে কিছু পাঠানো, লোগো ব্যবহার। অনুরোধ লাগে: section 5-এর সব কাজ। প্রস্তাব: AI-এর জন্য নিজস্ব role (Super Admin নয়, কারণ Super Admin-কে কমানো যায় না)। মালিক চাইলে সব key দেবেন, কিন্তু route-এর allow-list আর "অনুরোধ" তালিকা tool layer-এ আটকানো থাকবে।

### 7. টেক প্যাক আর AI Center-এর জন্য যা নেই

1. ফাইলের ধরন কম: FileAsset-এ সাধারণ আপলোড নেয় শুধু JPG, PNG, WebP আর PDF, 10 MB পর্যন্ত (ফাইলের প্রথম byte দেখে চেনে)। টেমপ্লেটে বাড়তি .docx আর HTML। quotation-এর রেফারেন্স ছবি JPG/PNG, 512 KB আর 2400 pixel। লোগো PNG/JPG, 2 MB। AI ছবি পড়ে 5 MB পর্যন্ত। embroidery-র .DST/.EMB/.PES, artwork-এর .AI/.EPS/.SVG/.PSD, মাপের শিট .XLSX/.CSV, .ZIP কিছুই নেওয়া যায় না।
2. টেক প্যাক আলাদা জিনিস নয়: এখন এটি project থেকে তখনই বানানো PDF, জমা থাকে না (শুধু AuditLog-এ লেখা থাকে)। version নেই, অনুমোদন নেই, মাপের চার্ট (inch ও cm), POM, artwork বা লোগোর জায়গা, embroidery ও print spec, Pantone কিছু নেই। Size model-এ শুধু নাম আছে, মাপ নেই। Style-এ fabric শুধু একটি লেখা।
3. ইমেইল পাঠানো নেই: SMTP সেটিং শুধু `.env.example`-এ, কোড নেই। WhatsApp Business API নেই, শুধু wa.me লিংক। Telegram নেই। বাইরে থেকে বার্তা আসার (webhook বা bot) কোনো route নেই; WebhookEvent model পড়ে আছে।
4. বুকিংয়ের অনুমোদন ধাপ নেই: বুকিং বানালেই PurchaseOrder `OPEN` হয়ে যায়, PDF সাথে সাথে ছাপা যায়। PurchaseOrderStatus-এ শুধু OPEN, PARTIALLY_RECEIVED, RECEIVED, CLOSED, CANCELLED। DRAFT বা "মালিকের অনুমোদনের অপেক্ষা" নেই।
5. owner-only flag নেই: RBAC শুধু key ধরে চলে, টাকা লুকানোর নিয়ম কোডে বাঁধা। কোনো রেকর্ড বা অংশকে "শুধু মালিক দেখবেন" চিহ্ন দেওয়ার উপায় নেই। কর্মচারীকে টেক প্যাকের অংশ ধরে দেখানো বা দাম, ক্রেতার নাম লুকানোর ব্যবস্থাও নেই।
6. style ধরে কলার-কাফের ছক নেই: ছক থাকে বুকিংয়ে (BookingCollarSize, BookingCollarColour), পোশাকের রং × সাইজ গ্রুপে। style ধরে ভাগ হয় শুধু PurchaseOrderLineShare-এ (projectId, colorName, sizeName)। style বা project-এ কলারের মাপ জমা থাকে না।
7. Estimated CM নেই: আছে শুধু চুক্তিতে ঠিক হওয়া ProductionProject.cmRate আর লক্ষ্য দাম targetUnitCost। অর্ডারের আগের costing sheet বা আনুমানিক CM নেই। "estimatedCostPerPiece" আসলে এখন পর্যন্ত খরচ ÷ লক্ষ্য পিস, CM নয়।
8. AI Center নেই: AI খরচ বা token গোনার টেবিল নেই, বাজেট নেই, module ধরে on/off নেই, একটিই চাবি, model বাছাই শুধু 2টি env দিয়ে। এজেন্ট, prompt বা কথোপকথন রাখার model নেই।
9. AI-এর জন্য লগইনের ব্যবস্থা নেই: শুধু cookie সেশন। API token, service account বা IP সীমা নেই। AuditLog-এ "এটি AI করেছে" বলার আলাদা field নেই।
10. মালিকের অনুমোদন বা মোছার অনুরোধের জায়গা নেই: কোনো ApprovalRequest বা DeletionRequest model নেই। এখন শুধু ইনবক্সের NotificationLog আছে।
11. "delete" আর "manage" আলাদা key নয়: যেমন `production.manage` দিয়েই batch, চুক্তি, cutting report মোছা যায়। AI-এর জন্য আলাদা `*.delete` key বা gateway-তে route আটকানো দরকার।
12. Brand-এর লোগো শুধু একটি লেখা (Brand.logoUrl), ফাইল আপলোড বা "লোগো ব্যবহারে মালিকের সম্মতি" চিহ্ন নেই।
13. কিছু কাজ শুধু Server Action-এ, REST route নেই: পেটি ক্যাশ খোলা/বদল/বন্ধ, মালিকের টাকা যোগ/তোলা, ব্যাংক চার্জ, ব্যাংক মেলানো, একসাথে স্টাইল আর্কাইভ, টেক প্যাক notes-এর AI খসড়া ও সংরক্ষণ, চুক্তির আবার খসড়া, কাঁচামালের ছবি আপলোড। এজেন্টের জন্য এগুলোর route লাগবে।
14. packing list AI দিয়ে পড়া API-তে আছে, কিন্তু Deliveries স্ক্রিন এটি ব্যবহার করে না (`parse: false`)।
15. রিমাইন্ডার শুধু অ্যাপের ইনবক্সে যায়; push শুধু log মোডে।
